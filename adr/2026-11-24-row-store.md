# ADR: Shared state and the table catalog share one single-writer store with a sequence-numbered log

Date: 2026-11-24 · PR #2372 · Status: proposed (draft for review)

## Context

Wvlet has a columnar engine and an Iceberg warehouse for analytics. Two upcoming needs instead look like OLTP. First, small shared state: a benchmark lock and queue that coordinates benchmark runs across coding sessions on one machine, starting as `sqlite3` behind `scripts/bench-run`. Second, the planned table catalog: a single-writer commit log, entities as rows, a large file index as columns, reads pinned to a log position, and branches across the whole catalog. In the warehouse every write is an Iceberg commit that rewrites data, manifest, and metadata files, so one-row changes are slow and accumulate files. The runner's activity store uses SQLite through `sqlite-jdbc`, which exists only on the JVM. Design note: [`plans/2026-11-24-row-store.md`](../plans/2026-11-24-row-store.md).

## Decision

- **One store serves both.** A store is a `<name>.wvdb/` folder attached with `use '<path>.wvdb' as <alias>` (or a `store` property of the `wvlet` connector). The bench queue is its first user; the catalog builds on it. Analytics data stays in Parquet / Iceberg.
- **Pure Scala, not SQLite.** A SQLite connector (`sqlite-jdbc`, `dlopen` on Native, `node:sqlite`) was the cheapest option. It was rejected for the same reason the engine does not run on DuckDB: one implementation on every platform with no native library, semantics Wvlet owns and can prove, and a format the catalog can extend (sequence numbers, branches, columnar segments). It stays possible as an ordinary connector.
- **A log with one global sequence number.** Every commit is one CRC32C-framed log record with a `seq` that only grows across checkpoints and restarts. `seq` is the store's version: reads pin it, caches invalidate by it, and replicas will replay the same records. Checkpoints are installed with an atomic rename and a directory fsync; the current state is the highest valid checkpoint plus the valid log after it, with no pointer file. Log files are kept back to the oldest registered reader position.
- **MVCC by sequence range.** Every row carries `added_seq` / `removed_seq`; a read at N sees `added_seq <= N and (removed_seq is null or removed_seq > N)`. Row keys and log records carry a `branch` id, always `main` until the catalog adds branches, so branches need no format migration.
- **Two table layouts, no B+tree.** `layout: row` keeps a table in memory as a sorted map, durable through the log, for point lookups and compare-and-set. `layout: columnar` keeps a row-oriented delta plus immutable Parquet segments with per-segment min / max, compacted by the writer, for large predicate-scanned data such as the file index. Columnar segments reuse the engine's Parquet scan. Larger-than-memory data is columnar, so no page file is needed.
- **One writer, validated commits.** One process is the writer: embedded, whoever holds an exclusive OS lock on the store's `lock` file; later, a catalog service. A transaction reads at `read_seq` and submits writes with conditions; the writer accepts it only if the row versions it read are still live, so accepted commits are serializable. Pure appends carry no condition and never conflict. A statement that reads and writes (`order by ... limit 1 update`) runs at the writer and cannot conflict. Readers take no lock.
- **`transaction { }` locks up front when embedded.** The compiler sees a whole block, so a writing block takes the writer lock before its first statement and always validates. This is a fast path over the same validated commit, so the same block can later be sent to a catalog service.
- **Compare-and-set is an `update`.** `order by` / `limit` before `update` and `delete`, plus a `select` after a write that returns the changed rows, make "claim the oldest queued row" one statement whose empty result means another session won. A failed `test` inside `transaction { }` rolls it back.
- **Only file primitives go to uni first.** uni gets `FileHandle` (positional I/O, truncate, sync), `FileLock`, `syncDirectory`, `moveAtomic`, and `CRC32C`, which encode no policy. The log incubates in Wvlet (`wvlet.lang.store.log`) and graduates to uni once its API settles; tables, MVCC, and validation stay in Wvlet. Native uses `fcntl` record locks, not `flock`, so a native `wvc` and a JVM `wvlet` exclude each other. Node.js reads only, because it has no lock API that excludes other platforms.

## Consequences

- `wvlet run` can serve the bench queue on the JVM and Scala Native with no SQLite install, and the queue's files are already in the catalog's format.
- The v1 format carries more than the queue needs (sequence ranges, branch ids, retained log positions, conditions in commit records). That costs memory for old row versions while readers pin them, bounded by expiring registrations.
- Writes are serialized through one writer per store. Network file systems and writes from more than one host are unsupported.
- On macOS, JVM commits survive a process crash but may not survive a power loss, because `FileChannel.force` does not issue `F_FULLFSYNC`; Native commits use it.
- One Lean model family (`WvletFormal/Store/`: log and recovery, commit validation, MVCC visibility, claims) gates the store and is extended by the catalog's branch, replica, and GC models. Changes to those areas update the model first.
- The store is new storage rather than a plan rewrite, so it has no `Optimization` toggle; planner changes that use it (`store_point_lookup`, `store_segment_pruning`) do.
- Moving the activity store onto this store is possible later and would make activity claims work on Scala Native; it is a separate decision because the activity state machine is Lean-gated.
