# ADR: Small shared state lives in a single-writer row store with a write-ahead log

Date: 2026-11-24 · PR #TBD · Status: proposed (draft for review)

## Context

Wvlet has a columnar engine and an Iceberg warehouse for analytics. Some workloads instead need SQLite's strengths: a few kilobytes to tens of megabytes of shared state, one-row reads and writes, several processes on one machine writing, and transactions. The first one is a benchmark lock and queue that coordinates benchmark runs across coding sessions on a Mac and a GB10 GPU host; it starts as `sqlite3` behind `scripts/bench-run`. In the warehouse every write is an Iceberg commit that rewrites data, manifest, and metadata files and keeps the old ones, so a one-row claim is slow, grows the folder without bound, and has no lock to wait on. The runner's activity store already uses SQLite through `sqlite-jdbc`, which exists only on the JVM. Design note: [`plans/2026-11-24-row-store.md`](../plans/2026-11-24-row-store.md).

## Decision

- **A new row store, separate from the warehouse.** A database is a `<name>.wvdb/` folder attached with `use '<path>.wvdb' as <alias>` (or a `rowstore` property of the `wvlet` connector). Analytics tables stay in Iceberg; the row store is for small mutable state and is not readable by other engines.
- **Pure Scala on uni, not SQLite.** A SQLite connector (`sqlite-jdbc`, `dlopen` of libsqlite3 on Native, `node:sqlite` on Node.js) was the cheapest option, and it was rejected for the same reason the engine does not run on DuckDB: one implementation on every platform with no native library, and semantics Wvlet owns and can prove. It stays possible as an ordinary connector later.
- **A write-ahead log plus checkpoint snapshots, not a B+tree.** Tables are kept in memory, made durable by a CRC32C-framed redo log with one frame per transaction, and checkpointed into a new snapshot generation that is installed with an atomic rename and a directory fsync. The highest valid snapshot generation is current; there is no pointer file. Recovery replays whole frames and truncates a torn tail. This is small enough to model in Lean and to test by truncating files at every offset. A B+tree page file is a later format version if data outgrows memory.
- **One writer at a time, lock-free readers.** A write transaction holds an exclusive OS lock on the store's `lock` file; readers take no lock and see the last committed transaction at each statement's start. Writes are serializable; read-only transactions see one snapshot. The OS releases the lock when a writer dies, and the next writer recovers.
- **The compiler takes the lock for a whole `transaction { }` block.** Because the block is compiled at once, a block that writes locks before its first statement, so there is no deferred-to-write upgrade and no `SQLITE_BUSY_SNAPSHOT`-style failure. Single statements autocommit.
- **Compare-and-set is an `update`.** `order by` / `limit` before `update` and `delete`, plus a `select` after a write that returns the changed rows, make "claim the oldest queued row" one atomic statement whose empty result means another session won. A failed `test` inside `transaction { }` rolls the block back.
- **uni gets the platform primitives and the log; wvlet gets tables.** uni adds `FileHandle` (positional I/O, truncate, sync), `FileLock`, `syncDirectory`, `moveAtomic`, and `CRC32C` in `uni-core`, and `WriteAheadLog` / `Checkpoint` in `uni`. Native uses `fcntl` record locks, not `flock`, so a native `wvc` and a JVM `wvlet` exclude each other. Node.js gets read-only access, because it has no lock API that would exclude other platforms.

## Consequences

- `wvlet run` can serve the bench queue on the JVM and Scala Native with no SQLite install, and `bench-run` can move off `sqlite3` without changing its schema or claim semantics.
- Writers are serialized per store. That suits coordination state and rules out write-heavy OLTP; there are no secondary indexes or larger-than-memory tables in the first version.
- Network file systems and more than one host are unsupported, since their locks are unreliable.
- On macOS, JVM commits survive a process crash but may not survive a power loss, because `FileChannel.force` does not issue `F_FULLFSYNC`; Native commits use it.
- A new Lean model (`WvletFormal/RowStore/`) gates the commit, recovery, and claim logic, and changes to them update the model first.
- The row store is new storage rather than a plan rewrite, so it has no `Optimization` toggle; planner shortcuts for it (point lookups) do.
- Moving the activity store (`SQLiteItemStore`) onto the row store is possible later and would make activity claims work on Scala Native, but it is a separate decision because the activity state machine is Lean-gated.
