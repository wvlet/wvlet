# ADR: Morsel-driven parallelism in the columnar engine

Date: 2026-11-22 · PR #2210

## Context

After column pruning and faster kernels, `wvlet-engine` ran TPC-H sf=1 in 8.6 s on one thread, against 0.33 s for DuckDB on all cores. The profile showed most time spent decoding Parquet row groups, evaluating filters and projections, probing hash joins, and aggregating. All of these are independent per row group. The engine is pull-based (`Operator.next()`) and cross-platform: Scala.js has no threads.

## Decision

- **Morsels are a source's own parts.** `TableSource.scanSplits` cuts a scan into independent parts. For a single Parquet file these are the row groups that row-group pruning keeps (`selectRowGroups`, then `readRowGroup` per part). Datasets and other sources don't split yet.
- **Plans keep their shape.** A post-planning pass (`Parallelizer`, run after `ColumnPruner`) finds *pipelines*: a splittable scan with the Filter / Project / hash-join probe operators above it. It replaces each pipeline with a `MorselOp`. A `MorselOp` rebuilds a fresh copy of the pipeline over each part and runs the copies as tasks. There is no push-based rewrite of the engine: operators above a pipeline still pull on the calling thread.
- **Output stays deterministic.** `MorselOp` keeps up to twice the parallelism of parts in flight and emits results in part order, so the output equals the sequential output (LIMIT without ORDER BY and spec outputs stay stable).
- **Hash joins share one build.** Probe-side splitting applies to joins whose output for a probe row depends only on that row: inner, left, semi, anti and cross. The build (`JoinBuild`) is made once, before any part starts, *on the calling thread*. It is then read-only and shared by the copies. Right and full joins split too. Their copies mark matched build rows in an array the build shares, which they only ever set to true. Once every part has finished, a *tail* copy of the pipeline runs over an empty input on the calling thread and emits the unmatched build rows, through whatever operators sit above the join (PR #2214).
- **Aggregation runs in two phases** when every aggregate's partial results combine with another aggregate:
  - count is combined by sum; sum, min and max by themselves; avg as a sum and a count
  - each part aggregates on its own, a final `HashAggOp` combines the partial rows by key, and a projection restores the original types
  - other aggregates (DISTINCT, quantiles, string_agg, ...) keep the sequential plan
- **Hash tables partition by key.** A large join build (at least 64K rows) is split by the hash of its key into 2× parallelism partitions. Each partition's table is built as its own task, and probes route rows to their partition. Grouped aggregations, the final phase of two-phase aggregation included, partition their input the same way, so groups never span partitions and any aggregate works (DISTINCT, quantiles, ...). The partition comes from the hash's top bits, which a partition's own table never uses as slot bits. Below 64K rows, aggregation stays on one thread in first-seen group order (PR #2218).
- **Sorts merge sorted runs.** A sort of at least 64K rows cuts its input into one contiguous chunk per thread. Each chunk is sorted (stable) and cut to the limit as a task. When the limit is at most 1/8 of a chunk, the chunk keeps a bounded max-heap of its top rows by (key, row index) instead of sorting fully. The merge of the runs is split into one output range per thread: on the calling thread, a splitter search finds for each range boundary the cut in every run, ordering rows by (key, run, position), so ties go to the earlier chunk. Each range is then heap-merged and gathered into batches as one task. So the output, top-N included, equals the sequential stable sort. Outputs below the sort threshold keep a single merge.
- **Windows split by the PARTITION BY key.** For a window call with PARTITION BY over at least 64K rows, rows are split by the top bits of the key hash (`GroupTable.partitionRows`), and each part's window partitions are grouped, sorted, and evaluated as a task. Each part writes only its own rows' slots of the output column, so the result doesn't depend on scheduling. Calls without PARTITION BY stay sequential. Rows are routed to parts in parallel too: each chunk counts its rows per part, then scatters them at its offsets, which keeps the row order. Column pruning passes through windows, so the scan below reads only the columns that the window calls and the operators above use. Window results are written to a primitive array of their type's vector layout (Bool, Int32 / Date, Int64 / Timestamp, Decimal, Float64, Str) instead of boxed values: ranking functions set them directly, and aggregates and value functions (lag, lead, first_value, ...) copy them from the source vector. Decimals that overflow an unscaled Long go to an overflow array that is allocated up front, so no task changes the column's storage. Partition rows are sorted with a stable merge sort on `Array[Int]` (`IndexSort`, shared with `SortOp`), and each parallel part reuses the key hashes that split the rows instead of hashing the keys again. Aggregates over frames that start at UNBOUNDED PRECEDING (running totals under the default frame with ORDER BY, and ROWS / RANGE frames from UNBOUNDED PRECEDING) fold one accumulator per partition: each row feeds only the rows between the previous frame end and its own, and rows with the same frame end share one result, so a partition costs O(n) instead of O(n·frame). This needs accumulators that fold rows in order and whose `result` leaves their state unchanged, so the values (floating-point sums included) equal those of recomputing each frame; aggregates whose result copies or sorts the collected rows (string_agg, array_agg, quantiles, mode) still recompute each frame. Sliding ROWS frames bounded on both sides (`rows[-N,M]`) fold counts (count, count_star, count_if) and sums with an Int64 or Decimal result (sum, sum_if) with two pointers that add the rows entering the frame and remove the rows leaving it, on wrapping Long arithmetic. That is exact whenever no frame's left-to-right fold can overflow, so each partition first checks that the absolute values of its summed rows add up to less than a Long (and that every decimal has an unscaled Long at the result scale); a partition that fails the check recomputes each frame, which keeps the integer overflow error and the decimal switch to BigDecimal exactly where they were. min, max, max_by, and min_by over the same frames find each frame's winning row with a monotonic deque of row positions, O(n) per partition: the per-frame fold keeps the first non-NULL value and replaces it only on a strict improvement, so it ends on the leftmost best row, and the deque keeps equal rows so its front is that row. Float64 min / max compare with primitive `<` / `>`, under which a NaN is never replaced and never taken, so a frame whose first non-NULL value is NaN returns NaN. The winning rows are then fed to one MinMax / ByKey accumulator with one group per output row, so values, NULLs, and the choice between equal-comparing values (-0.0 and 0.0, decimals of different scale) come from the same code as recomputing each frame. Float64 sums, avg, and other sliding aggregates still recompute each frame, since removing a double changes the result bits. The `wvlet.engine.parallelSortMinRows` and `wvlet.engine.parallelWindowMinRows` properties lower both thresholds, and the parallel tests set them to 1.
- **Semi / anti joins probe the larger side.** When an EXISTS / IN subquery is estimated at over 4x the outer input, the hash table holds the outer rows instead (RIGHT SEMI / RIGHT ANTI). The subquery's rows are probed in parallel parts, which mark the matches, and the tail emits the matched (or unmatched) outer rows once.
- **Tasks never wait on tasks.** Everything a part needs from other operators (join builds) is prepared before parts are submitted. So a fixed thread pool can't deadlock, even when a build input is itself a `MorselOp`.
- **Pipelines also start above grouped aggregations** (`parallel_above_breakers`). The output of a grouped aggregation (partitioned, or the final phase of a two-phase one) is a source whose parts are its output batches (`BreakerSource`), so the filters, projections, join probes, and partial aggregations above it form a pipeline like those over a scan. A partitioned aggregation emits at least one batch per key partition, so there are about 2× parallelism parts. The aggregation is drained when the `MorselOp` above it starts, on the calling thread before any part is submitted, as join builds are, so tasks still never wait on tasks. Parts are emitted in batch order, so the output equals running the operators on the calling thread. An aggregation with nothing above it to run (directly under a sort, or a join build input with no probe) stays as it is.
- **Shared CTE results are computed concurrently** (`concurrent_shared_ctes`). A shared result (a CTE read more than once, the input of grouping sets) is computed once, by the first thread that asks for it, while other threads asking wait for it (`ComputeOnce`). When several results are needed together, they start at once on *coordinator* threads: the CTEs that joins read when the planner computes them to order the joins again, and, when the plan starts running, the results nothing has computed yet (`StartSharedOp` at the plan's root). Each coordinator drains a CTE body, whose `MorselOp`s submit parts to the shared pool. Coordinators are plain threads outside the pool (at most half the parallelism; `TaskRunner.coordinate`), so only coordinators and the calling thread ever wait, never pool tasks. Results start in dependency order, producers first. A reader that reaches a result no coordinator has started yet computes it itself, so the coordinator limit can't make readers wait forever. A failure stays with its result and is raised only when a reader reads it, so a CTE that a query never reads can't fail it. Closing the plan drops the coordinators that haven't started and waits for the running ones. Results and their order are unchanged, as each result is still computed once and read the same way.
- **The runner is platform code.** `TaskRunner` is a fixed daemon pool on JVM and Scala Native (`TaskRunnerCompatImpl`), sized by `WVLET_ENGINE_PARALLELISM` / `wvlet.engine.parallelism` or the processor count, plus a smaller pool for coordinators. Scala.js runs tasks and coordinators sequentially as they are submitted, so the same plans run unchanged.

## Consequences

- TPC-H sf=1 dropped from 8.6 s to 2.1 s (6.4x DuckDB's total, from 26x). See `plans/2026-11-21-columnar-engine.md`.
- Expressions must be safe to share across threads. They are immutable apart from benign caches: `Const`'s last vector, and the synchronized regex cache. New expressions must keep it that way.
- Parallelism is per operator, not across the whole plan: operators above a pipeline pull on the calling thread, and parallelize their own work (partitioned aggregation, sorts, windows) internally. Above a grouped aggregation, a new pipeline starts over its output; above a sort or a window, operators still run on the calling thread. A sort still merges its runs, and a window without PARTITION BY evaluates, on one thread.
- Outer hash joins build on the smaller input. When the build side is estimated to be over 4x the probe side, LEFT becomes RIGHT (and back) with the inputs swapped, so the large input is probed in parallel. TPC-H q13 went from 395 ms to 62 ms this way.
- `EngineTPCHParallelTest` rewrites the TPC-H data in 2048-row row groups, so that every query exercises the parallel paths against DuckDB.
