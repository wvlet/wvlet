# Engine spill framework and partitioned hash aggregation spill

## Goals

- Let the engine finish queries whose working set exceeds memory, instead of failing with RESOURCE_EXHAUSTED or an `OutOfMemoryError`: TPC-H and TPC-DS SF100 with an 8 GB heap is the bar of the "Wvlet engine at SF100" goal, and this PR is its item 5.
- This PR: one shared spill framework (format, trigger, temp files, cleanup) plus its first user, `PartitionedAggOp`. Grace hash join, external sort/window, and shared CTE results follow as separate PRs on the same framework.
- Nothing changes when nothing spills: same plans, same SF10 timing.

## Background

- `MemoryContext` (#2573–#2575) counts the large holders per query and throws RESOURCE_EXHAUSTED past the query limit; nothing degrades. Reservations are held until the query closes. CLI and REPL runs have no limit unless set; the server's pool defaults to 70% of the max heap. Aggregations inside morsel parts and with `memory_accounting` off run under `MemoryContext.NoOp`.
- `PartitionedAggOp` reads its whole input into memory before it routes rows to partitions by key hash (`readInput`, deferred columns left deferred), and each partition then runs a `HashAggOp`. The buffered input, not the group tables, is most of its memory, and the hash partitions are a natural spill unit (every group lives in one partition).
- A parallel session (early memory release) is adding `MemoryContext.child()` / `release()` so holders return bytes mid-query (uncommitted in its worktree today); #2577 adds the low-memory killer. Spilling needs that release.
- DuckDB spills aggregations, joins, sorts, and windows under `memory_limit` with its own block format; DataFusion spills sorts and aggregations in Arrow IPC files. Neither uses Parquet for spill: spill files are written once, read once, and deleted.

## Design

Lane: Standard — a new engine behaviour (disk writes during queries), a new option, a new on-disk format, and an always-gate area (query data written to and deleted from a temp directory).

- **Release first.** Spilling holders reserve through a child context and release it after spilling. If the early-release PR has not landed when this one is ready, this PR adds the minimal `child()` / `release()` and the other PR rebases on it (coordinated through the goal).
- **Trigger: a soft spill threshold below the hard limit.** Spillable holders ask `tryReserve(bytes)`: it reserves nothing and returns false when the query would pass its spill threshold. The holder then spills and releases. Non-spillable holders keep `reserve` and the hard limit. On `NoOp`, `tryReserve` always succeeds, so morsel-part aggregations and `memory_accounting` off never spill.
- **Pool pressure is not a trigger in this PR.** The pool's capacity stays soft as documented (admission and the killer handle it). Spilling under pool pressure is a follow-up once the killer has landed, so the two don't race.
- **Where the threshold comes from.** `WvletEngine.withSpillThreshold(bytes)` / `noSpillThreshold()`; default the smaller of the query limit and half of `Runtime.maxMemory` on the JVM, or `-Dwvlet.engine.spillThreshold=<bytes>`. Native has no heap cap by default (Immix), so Native has no default threshold and spills only when one is set. Hard limits stay unset by default.
- **Format: a raw columnar block format of engine vectors**, not Parquet. Each block is one batch: per column its type, nulls, and values as held in memory. Strings held as per-batch `entries` are written as the entries plus codes. Every other string (plain, Parquet-coded, shared-dictionary) is written as UTF-16 chars with a length per row: exact for any `String`, including lone surrogates, with no encoding pass. Shared-dictionary code identity is lost on read-back, which only costs grouping speed. `ObjVec` columns (nested `AnyT` values, wide decimals) are not spillable in this PR: an aggregation whose input holds one falls back to `reserve`. No compression yet (LZ4 is a follow-up if disk bandwidth shows in profiles).
- **Spill files are per query and cleaned up with it.** A per-query `SpillSpace` creates `<spill dir>/wvlet-spill-<random>/` lazily on the first spill, owner-only (0700 directory, 0600 files on POSIX). When the query's context closes (success, failure, or kill), it deletes only the files it created inside that directory, then the directory. It first marks itself closed, so later appends and reads fail. Writes run on the aggregation's reader thread, so no writer is still running at close. A JVM shutdown hook is the backstop. The spill dir defaults to `java.io.tmpdir` and is set with `WvletEngine.withSpillDirectory`. A per-query disk cap is a follow-up.
- **Platforms.** JVM and Native write files through a `SpillCompat` trait with per-platform copies under `.jvm/` and `.native/`, as `TaskRunnerCompatImpl` does. Scala.js has no spill: `tryReserve` behaves like `reserve`, so JS behaviour is unchanged.
- **Aggregation spill (this PR).**
  - When `PartitionedAggOp`'s input read hits the threshold, it switches to spill mode, also on its single-thread path (small parallelism or few rows estimated): it compacts each buffered and remaining batch as it routes it by key hash into 64 spill partitions, appends each partition's rows to its file, and releases the buffers' reservations once all of them are spilled.
  - Tasks hash, gather, and encode chunks of the input; the reader thread appends their blocks to the 64 files in chunk order. So there are no shared appends, no writer is running at close, and a partition's rows keep the input order. Plain strings at most half distinct per block are written as entries plus codes.
  - Each file records the `estimatedBytes` of what it holds. Partitions are read back in waves sized from those estimates against the threshold, aggregated through the existing `HashAggOp` path, and their files deleted once their groups are emitted.
  - Waves get at least a quarter of the threshold. A wave of one partition runs the in-memory parallel path over it; a wider wave runs one task per partition. A partition whose estimate (twice its rows' bytes) exceeds half the threshold is re-partitioned once with a different hash seed before it is read. Past that it runs anyway and meets the hard limit (RESOURCE_EXHAUSTED). Group-table growth still uses `reserve`, so groups that outgrow the estimate also meet the hard limit.
  - Sorted splits and packed routing apply only to the in-memory path; spilled partitions pack their own keys from their ranges, as unrouted partitions do today. Output order is unspecified for aggregations, and it changes only when the query spills.
  - Not covered: plain `HashAggOp` (global aggregates and other non-partitioned plans; their state is per group, not per input row) and `DistinctOp`; listed as limits.
- **Toggle.** `spill_aggregation` (on by default, listed in `OptimizerOptionsTest`, a `noPlanChange` entry). Off means `PartitionedAggOp` reserves as today. The framework itself is inert until a holder uses it.
- **Default on and "nothing changes".** Before calling SF10 timing unchanged, check each SF10 query's peak `reservedBytes` against half the bench heap (no query may spill by default) and record it in the PR.
- **How the next items reuse it.**
  - Grace hash join: the same hash-partitioned spill writer over build and probe with one seed, joining partition pairs one at a time; runtime filters are built before the build spills.
  - External sort and window: each sorted run is one spill file; a k-way merge streams the runs back; top-N stays in memory.
  - Shared CTE results: left to that item (raw blocks, or Parquet for row-group pruning by readers).
- **Docs.** A Spilling section in `design/engine.md` (the threshold, `tryReserve` on `NoOp`, the soft pool); one ADR for the framework (format, trigger, temp files) and one for the aggregation spill (input rows, 64 partitions, one re-partition), per the goal's one-ADR-per-operator rule; a short user-docs paragraph on when queries spill, where the files go, and how to change the directory and threshold.
- **Tests.** Format round-trips per `PType` (nulls, each string form, empty batches); aggregations forced to spill with a tiny threshold match DuckDB (spec/tpch and TPC-DS aggregation queries), including the single-thread and re-partition paths and an `ObjVec` input falling back; the spill directory is gone after success, failure, and a kill with tasks mid-write. SF10 A/B with the toggle when nothing spills, and an SF10 run with a small threshold to show the spilling cost.

## Off-heap memory and buffer reuse (uni Canvas)

- uni 2026.3.18's `Canvas` gives Long-addressed buffers outside `-Xmx`, freed by `close()`, on all three platforms. On the JVM it needs Java 22+, and each `newOffHeapCanvas` opens its own shared `Arena`, which zero-fills the memory and closes with a cross-thread handshake.
- Probe (JDK 25, M-series Mac, load ~12, so the numbers are rough; time per op): a new heap `Array[Long]` vs a new off-heap canvas plus `close()`: 64 KB 2.8 vs 10 µs, 1 MB 18 vs 24 µs, 16 MB 787 vs 221 µs (a G1 humongous allocation), 128 MB 1.1 vs 2.2 ms. Writing a reused buffer costs the same through a canvas as through an array: 16 MB 319 vs 311 µs, 128 MB 2.55 vs 2.68 ms. Bounds checks don't show in sequential `writeLong` loops.
- So the win is reuse, not off-heap: a reused buffer skips allocation and zeroing whether it lives on the heap or off it. Off-heap adds memory outside `-Xmx` with no GC tracing, and buffers over 2 GB. Allocating a fresh canvas per structure is slower than a heap array below ~16 MB.
- This PR keeps spill blocks on the heap: one encode buffer per block (≤ ~1 MB), short-lived and small next to the disk write. Reusing one buffer per writer is a cheap follow-up.
- Proposed as its own item, after a profile shows the gain: an engine `SegmentPool` of large reused segments (heap arrays on JDK < 22 and Scala.js, off-heap canvases where supported), acquired and released without closing, with its size counted in `MemoryContext`. Callers: join build entries, aggregation state, and spill buffers. Flat tables still need a cleared empty state on reuse (a fill, or generation tags), so the pool avoids allocation and GC, not all zeroing.
- With breaker state off-heap, the default spill threshold can no longer come from `-Xmx` alone; it would come from one engine memory size (as DuckDB's `memory_limit`) split between heap and the pool. The `tryReserve` trigger and spill files don't change.
- The compact-strings session confirmed the numbers (best of 5: 64 KB 11.4 vs 0.7 µs, rising to 164 µs with 12 busy threads from the shared-arena close handshake). A pooled segment costs ~0.02 µs, and re-zeroing one costs about the same as a new array. Hashing through `Canvas.readLong` is 18–40% slower than `byte[]` plus a VarHandle. Strings stay on the heap (StrVecs have no single owner to call `close()`). So the pool targets single-owner buffers: spill blocks, join flat tables, and group tables. TPC-DS allocates ~3 GB in `GroupTable` empty slots, zero-fill that a pool would skip.
- A uni change (non-zeroing allocation, or one arena per allocator instead of per canvas) would make fresh canvases cheaper. It's worth proposing only if the pool shows that allocation, rather than reuse, matters. To be coordinated with the compact-strings item, which is weighing Canvas for string bytes.

## Alternatives and Why Not?

- **Spill as Parquet through uni's writer.** Reuses code and compresses, but encoding and decoding cost several times a raw copy, it cannot keep dictionary codes as the engine holds them, and spill files never leave the process.
- **Spill partial aggregation state instead of input rows.** Smaller files for heavily reducing aggregations, but needs serialization and merge for every accumulator; `PartitionedAggOp`'s memory is its buffered input, which raw rows cover with one format.
- **Spill only when the hard limit throws.** Leaves no headroom for the read-back wave and makes the error path the control flow; a separate threshold keeps the limit as the safety net.
- **Spill off by default (only with an explicit threshold).** Safer for disks, but a laptop CLI user would still hit OOM on SF100 without knowing the option exists.
- **Off-heap or memory-mapped spill.** Not available on Scala.js or uniformly on Native, and the bar is an 8 GB heap, not zero-copy.
