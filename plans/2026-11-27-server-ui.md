# Wvlet server UI: query monitor, editor, plans

## Goals

- Give the wvlet server a web UI that shows what the server is doing: which queries run, wait, and finished, how long they took, how much memory they hold, and why they failed, like Trino's coordinator UI.
- Let people write and run queries in the same UI, look at the plan, and reopen a past query in the editor.
- Serve it from the server, started by `wvlet server`, not from the playground, and build it on uni-dom + uni-ui like the playground.
- Replace the outdated `wvlet-ui` / `wvlet-ui-main` app (MainFrame + FlowRunsPage, Monaco, DuckDB-Wasm) instead of extending it.

## Background

- The server API (`FrontendApi`) has `status`, `submitQuery`, `getQueryInfo`, and `cancelQuery` only. There is no way to list queries; a client must already know an id.
- `QueryService` keeps each query's `QueryInfo` (status, times, errors, result rows) for `finishedQueryRetention` (1 h) or the newest 1000 finished queries. It does not keep the query text, session, or profile: those go only to the CREATED event in `<target>/logs/query-events-yyyy-MM-dd.jsonl`.
- Memory: each in-process engine query opens a `MemoryContext` inside `WvletEngine.execute` with a peak (`peakBytes`, #2578), but the server never sees it. `MemoryPool` knows the total reserved bytes, capacity, and open queries; it does not count low-memory-killer kills.
- Plans: the engine's `Operator.explain` is already flow-style (↓ / ↙, the playground's `PlanView` parses it), but the server only writes it to the debug log. DuckDB and Trino connectors report their SQL through `QueryProgressMonitor.newQuery(sql)`, but the server runs queries with a no-op monitor, and the monitor comes from the session runner's shared `Context`.
- `QueryInfo.sql` and `queryFragment` exist but `QueryService` never sets them.
- The old app also hosts the documented **Flow Runs** page (`wvlet ui -w <folder>`, [flow.md](../website/docs/syntax/flow.md)), and the playground depends on `wvlet-ui-main` for its Monaco editor binding.
- Ids stay `String` on the wire ([ADR](../adr/2026-11-27-trino-style-query-ids.md)): uni's router ignores custom Weavers. Ids sort by creation time, so they work as a paging cursor.
- The server starts today with `wvlet ui` (JVM CLI only, `WvletMain.ui`; on macOS it also opens a browser). Docs, the bundled skill, `for-ai-agents.md`, and `WvletCli.jvmOnlyCommands` all name `ui`.
- All RPCs are POST and need the bearer token when `--auth-token` is set; static assets are served without it.

## Design

Lane: **Standard**: new API methods and new screens; the list exposes every session's query text to any token holder (security boundary), and stage 2 changes packaging.

### User flow

- An operator starts `wvlet server` (optionally `--auth-token`) and opens `http://localhost:9090`. With a token set, the UI asks for it once and keeps it in the browser's session storage.
- **Overview** (landing page): running / queued / finished counts against the limits, memory pool used vs capacity, query-worker and engine-thread load, heap, low-memory-killer kills, uptime. Refreshes every second.
- **Queries**: newest first, filterable by status, session, profile, time range, and text; each row shows id, state, user-visible query head, queued and run time, rows, peak memory. Running rows update live.
- **Query detail**: full query text, generated SQL, engine plan, timeline (created → started → completed), result rows, errors with their source location, current and peak memory. **Cancel** for queued/running queries; **Open in editor** for any query.
- **Editor** (stage 3): write and run, run the selection or the statement at the cursor, results grid, plan tab drawn source-first like `LogicalPlanPrinter` (↓ / ↙, not nested trees). Runs go through `submitQuery`, so they appear in the query list too.
- Recovery: a failed query keeps its error in the detail page; an evicted query (past retention) shows "no longer kept" with its id.

### Stage 1: backend API (this PR)

- CLI: `wvlet server` starts the server and its UI with today's `ui` options and prints the URL; `--open` opens a browser. `wvlet ui` is removed (no alias); docs, `for-ai-agents.md`, the skill, and `jvmOnlyCommands` switch to `wvlet server`.
- New `FrontendApi` methods, all keyed by `String` ids, existing methods unchanged:
  - `listQueries(filter)`: running and queued plus kept finished queries, newest first. Filters: statuses, session id, profile, created-after/before, text contains. Paging: `limit` (default 100, max 1000) and a page token (the admission number of the page's last query; ids can tie within a second).
  - `getQueryDetail(id)`: the summary plus query text, SQL, plan text, errors, and memory; no result rows (those stay in `getQueryInfo`).
  - `getClusterInfo()`: counts and limits, memory pool (reserved, capacity, open queries, kill count), worker load (running / max running), engine task pool load (busy threads / size), JVM heap, uptime, version.
- `QueryService` keeps the query text, session id, profile, and request id next to each `QueryInfo`, under the same retention, so the list needs no log reads.
- Memory and plan per query: the server installs a per-thread observer around `runStatement` (it runs on the query's worker thread, and so does `WvletEngine.execute`); `execute` reports each query context and its physical plan text to it. The server then shows live reserved bytes for running queries and the max peak across a statement's engine queries. With `memory_accounting` off, memory reads "not tracked", not 0.
- SQL for DuckDB/Trino: the same observer receives `newQuery(sql)` from the connectors, set per query instead of the session's no-op monitor; the server fills `QueryInfo.sql` too.
- Engine additions are plan-identical, so no `Optimization` toggle: `MemoryPool` counts kills (`killCount`), and the task runner exposes busy / total threads and waiting tasks.
- Live updates by polling: the UI calls `getClusterInfo` and `listQueries` every second. No change counter: running rows change every poll (elapsed time, memory), so it would rarely let a client skip work.
- Tests in `wvlet-server`: filters and paging, detail fields for finished / failed / cancelled queries, memory and plan capture on the in-process engine, cluster counts, RPC round trip of the new types.

### Stage 2: workload console with editor (second PR, revised after user feedback)

- User feedback on the first prototype (Overview / Queries / Detail pages): "almost the same as Trino's coordinator UI. Design it more sophisticated and reduce the number of user clicks so users can manage their workload at ease", and "there is no query editor so users can submit a new query". The editor moves from stage 3 into this PR.
- One screen, no page hops (`#/` with the selection in the hash, e.g. `#/q/<id>`; old `#/queries/<id>` links still open it; `#/flows` stays a second tab):
  - Health strip across the top: running/slots, queued, engine memory/pool, engine threads, heap, low-memory kills, each with a 2-minute sparkline. Clicking a tile filters the list (Running, Queued, Failed).
  - Filter chips with counts from the new `QueryList.facets` (status, session, profile; each facet counted under the other filters), a search box (`/` focuses it), and a Pause/Live toggle.
  - Rich rows instead of a plain table: status dot, query head, id, session, age, an inline time bar (queued amber + running blue, scaled to the slowest row in view), and a memory bar (relative to the largest in view, % of pool on hover). Hover actions: Cancel, Open in editor, Copy id. Checkboxes and a bulk bar ("3 selected · Cancel · Clear").
  - Inspector pane on the right for the selected query: facts, errors, tabs Query / Engine plan / SQL, Cancel, Open in editor. Selecting a row never leaves the list.
  - Timeline view (toggle with List): a Gantt of the visible window, one lane per session, queued vs running segments, a now-line; clicking a bar selects the query.
  - Editor: a bottom (or toggleable) panel using the playground's Monaco binding (`wvlet.lang.ui.component.monaco.MonacoEditor`, now in `wvlet-ui`; see `wvlet-ui-playground/.../CodeEditor.scala` for usage, and `main.js` must import `MonacoEditor.ts`/`WvletLanguage.ts` and set `window.MonacoEditor` before starting Scala.js). Run all (⌘/ctrl-Enter), run selection or statement at cursor (via `QueryRequest.querySelection` / `linePosition`), a per-tab session id, results grid (uni-ui `DataTable`, like the playground's `ResultPanel`) from `getQueryInfo` result rows, the run shows up in the list live. "Open in editor" loads a past query's text.
  - Keyboard: j/k or arrows move, Enter opens, x checks, c cancels (press twice to confirm), Esc closes the inspector, / search.
- Fixed in this PR along the way: the server answered every non-POST request with 400, so the static UI was never served (non-RPC paths now go to the static handler); static files went out as `application/octet-stream` (the content now carries the type), which made browsers refuse the module scripts.
- Module layout: `wvlet-ui` holds the pages and the Monaco facade (tested in Chromium); `wvlet-ui-main` is the thin Vite entry the CLI packs into `web/` (packaging paths unchanged); the playground depends on `wvlet-ui`, not `wvlet-ui-main`. MainFrame, Tailwind, DuckDB-Wasm, FileNav, and the old editor are removed.
- Screenshots of each view in a real browser (headless Chromium via Playwright is fine) after `uiMain/fastLinkJS`, and the packaged build (`cli/packQuick`, served by `wvlet server`).

### Stage 2b: visual redesign (next PR)

- User feedback on the stage 2 console (2026-11-27, PR #2596 approved and merged as is): "UI is still far from my standard as it's not refreshing at all from Trino's coordinator UI. We can merge for now, but need a significant change to the overall design".
- The one-screen layout, fewer clicks, and the editor stay; the visual language (dense table rows, tile strip, plain panels) needs a fresh direction. Start the next PR with a design note showing 2-3 distinct visual directions (mockups or screenshots) before coding.
- Open items from the stage 2 review: Flow runs still uses the plain table; editor session chips stay one per tab (user chose "Leave as is"); row and bulk Cancel stay one click (user chose "Keep one click").

### Stage 3: plan view (third PR)

- Plan view drawn source-first like `LogicalPlanPrinter` (↓ / ↙), reusing the playground's `PlanView`, in the inspector and the editor.

### Follow-ups (out of scope)

- Per-operator runtime stats in the engine (rows, time, memory per operator; EXPLAIN ANALYZE-style), shown on the plan view.
- History past the in-memory retention, read from the daily event logs.
- Server-sent events instead of polling, if one-second polling costs too much with many open browsers.
- Per-user access control: today any token holder sees every query.

## Alternatives and Why Not?

- Server-sent events now: uni's RPC handler answers one JSON response per POST; streaming needs a new non-RPC handler and auth path. Polling a small JSON every second is enough for one server.
- Read the list from the jsonl event logs: slower, and misses live state; in-memory state already has it within retention.
- Return memory and plan through `QueryResult`: the runner's result types are shared with the CLI and REPL; a thread-local observer keeps them unchanged and also gives live bytes while the query runs.
- Extend the old `wvlet-ui-main` app: it is built on Monaco, DuckDB-Wasm, and Tailwind with a page for flows; starting from the playground's uni-ui stack is less code.

## Preferences learned

- Context: server UI visual design. Chose: a refined dense-table console (health tiles, rows with bars, inspector). User chose: merge, but redesign significantly; it still reads like Trino's coordinator UI. Principle: for user-facing UI, propose distinct visual directions up front instead of iterating on the familiar admin-table look.

- Context: launch command for the server UI. Chose: new `wvlet server` with `wvlet ui` kept one release as a deprecated alias. User chose: remove `wvlet ui` outright. Principle: pre-1.0 CLI, prefer one name over compatibility aliases.
