# Close the GPU executor's remaining SF10 gaps to Sirius

## Goals

- Cut the remaining large SF10 gaps between the Wvlet engine + GPU and DuckDB + Sirius (pinned): q1 (127 vs 66 ms), q13 (76 vs 18 ms), and q18's group-by (65 vs 78 ms total, but its 48 ms group-by has a 20 ms sorted-key win).
- Each change is a `GpuFeature`, A/B'd on the Spark in one JVM, with results still matching DuckDB at SF10.

## Background

- From `WVLET_GPU_PROFILE=1` (PR #2366), q1 is Scan → Filter → Aggregate → Project → Sort over 60M lineitem rows. The filter keeps 59.1M rows and copies all 7 columns (49 ms), the aggregate arguments run ~10 elementwise kernels (45 ms), and the group-by over two 1-char string keys takes 32 ms.
- Each elementwise kernel over 60M INT64 rows costs ~3-4 ms on the GB10 (shared LPDDR5X), so q1's time is mostly memory traffic: copies and intermediate columns.
- q1's three `avg` calls each cast a 60M-row decimal column to FLOAT64 before cudf's `mean`.
- q18 groups all 60M lineitem rows by `l_orderkey` straight off the scan (48 ms). lineitem is stored sorted by `l_orderkey`; a microbenchmark gave 27 ms for cudf's sorted group-by (`withKeysSorted`) against 47 ms for hash.
- q13's 76 ms is a LEFT join with a residual. What remains after `prune_columns` is not profiled yet: the 15M-row inner-join gather maps, the scatter that finds unmatched left rows, the concatenate, and the group-by.
- CI does not build `wvlet-engine-gpu`; correctness comes from `GpuTPCHTest` on the Spark (spec/tpch and SF10 against DuckDB).

## Design

Lane: Express. An internal performance change to an optional example module, with each part behind a flag that is on by default and can be switched off; it touches no always-gate area. The launch prompt says not to merge, so the PR waits for the user.

- **`sorted_keys` (q18).** The column cache records, once per cached integer column, whether it is non-decreasing with no NULLs (one compare of adjacent rows, ~13 ms once). Device tables carry that flag per column; scans set it, and filters, limits, and plain column projections keep it. Joins, sorts, and key filters (semi-join gathers, which reorder rows) clear it. A group-by whose only key is such a column uses cudf's sorted group-by.
- **`masked_filter` (q1).** When an Aggregate reads a Filter that keeps most rows (at least half, from a count of the mask), the filter is not copied. Its mask (NULL as false) becomes one more group key, and the groups whose mask key is false are dropped from the result, which has only a few rows. Keys with NULLs of their own still group as before, and count(*) counts only the rows of each kept group. A global aggregation whose mask keeps no rows returns its one empty-input row as today.
- **`avg_as_sum` (q1).** `avg` of a decimal or integer is computed as an exact sum and a count per group, and divided in FLOAT64 over the few result groups. The gain is speed: it drops one FLOAT64 cast of the input per `avg`, and the sum reuses the `decimal_sum_split` and `decimal_narrow` paths. It falls back to today's path when the sum cannot be computed in 64-bit halves. The last digits can differ from the CPU engine's double sums; `GpuTPCHTest` compares with the tolerance it already uses for floats.
- **`dictionary_keys` (q1).** The first time a string scan column is a group key, the cache checks its distinct values. At most 2^15 values, and at most 1/16 of the rows, it keeps the sorted values and an INT32 code per row (counted in the cache budget, evicted with the column). Otherwise it remembers not to try again. A group key that is the unfiltered scan column groups on the codes, and the result keys are decoded from the dictionary over the result groups only.
- **`ast_exprs` (q1, if the above leave argument time).** Compile decimal and integer arithmetic trees into one cudf AST kernel (`CompiledExpression`) instead of one kernel per operator. Under `decimal_narrow`, decimals are unscaled INT64 at known scales, so the AST runs on their INT64 views. Kept only if its A/B wins after the first three.
- **q13.** Profile its join stages first, then fix what dominates behind its own feature; the likely target is the unmatched-left-rows step (scatter, NOT, filter) and the concatenate before the group-by.
- **Smaller gaps** (q5, q6, q12, q19: 2-8 ms each) get profiled after the main three, and a fix lands only if it is a small change; otherwise the PR reports where their time goes.
- **Chunked-scan PR (in flight on the same files).** Cache and scan edits stay small and separate from the rest. Sortedness and dictionaries are properties of a whole cached column; a chunked scan would read neither until its chunks carry them, so the features stay correct and only lose their gain there.
- **Validation and docs.** `GpuTPCHTest` on spec/tpch and at SF10; each feature's SF10 A/B has `rows_match=true` and no "GPU execution failed" lines; a final `gpu_offload` A/B. The ADR's consequences, the speedup plan's Status, the dgx-spark README results, and design/engine.md's Accelerators section get what lands and the new numbers. The features are internal flags of an example module, so `website/docs` does not change.

## Alternatives and Why Not?

- **Checking sortedness per query instead of in the cache:** 13 ms per check eats most of the 20 ms gain; the cache pays it once.
- **Dropping filtered rows by gathering only the key and argument columns:** still copies 59M rows of each read column; an extra BOOL8 key copies nothing.
- **Nulling out the keys of dropped rows:** setting a validity mask copies the key columns (strings in q1) and works only for keys without NULLs.
- **avg via FLOAT64 sums of the narrowed INT64 view:** still one cast per row.
- **Encoding all string columns:** costs memory and a dictionary build per column; only low-cardinality columns pay for it.
- **Writing fused CUDA kernels:** adds a native build to an example module; cudf's AST covers the same arithmetic.
