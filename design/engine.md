# Columnar engine

This page owns how `wvlet-engine` plans and executes Wvlet relations, and the gates an engine change must pass. Why the engine exists and why it executes typed plans instead of SQL is in [the columnar engine ADR](../adr/2026-11-21-columnar-engine.md); its optimizer decisions are the `adr/2026-11-2*-engine-*.md` records.

## Planning path

- Every relation is planned through the runtime IR in `wvlet.lang.engine.runtime`: `RuntimeBinder` → `RuntimePlan` → `Lowering` into physical operators (`wvlet.lang.engine.exec`).
- `Planner` (`wvlet.lang.engine.plan`) keeps the shared pieces the binder calls, generic over a plan builder: correlated joins, decorrelation, join ordering, and parallelization.
- `Planner` is split into traits it mixes in over its shared state (members they share are `private[plan]`): shared results and CTEs (`SharedResult`, `DeferredCTE`, `finalizeCTEs`) live in `plan/SharedResults.scala`, aggregations (grouping sets, IN-subquery group sharing, plan-time group totals) in `plan/PlannerAggregations.scala`, joins (join kinds and conditions, equi-join keys, USING, lateral unnest, ASOF) in `plan/PlannerJoins.scala`, ORDER BY keys in `plan/PlannerSortKeys.scala`, filters and subqueries (conjunct splitting, plan-time IN / EXISTS / scalar subqueries, decorrelation) in `plan/PlannerSubqueries.scala`, and the physical steps in `plan/PhysicalSteps.scala`. `Planner.lower` passes the toggles' flags to `Lowering`, and `optimizePhysical` configures the operators: column pruning, prefilters, the toggles' operator flags, and `Parallelizer`. The walks that set or clear operator flags (`Planner.disableLateGather`, ...) are `PhysicalWalkers`. A new operator-flag toggle goes there, and a flag that has to hold on both sides of Parallelizer is cleared in both of its passes.
- Logical passes (`PushDownFilters`, `PruneColumns`, `ReorderJoins`, `GroupKeySemiJoins`, `ShareSubplans`, `Normalize`, ...) run in `Optimizer` over the runtime plan. Rules with three-valued-logic subtleties have Lean models; see [formal verification](formal-verification.md).
- A shared CTE body is optimized before its readers' filters are known. Once they are pushed into it, `Optimizer.afterReaderFilters` (called from `DeferredCTE.lower`) runs the passes whose decisions read estimates those filters change (outer build sides, eager aggregation) again; a new pass of that kind is added there.
- Planner memo tables keyed by logical plan nodes miss the copies that `transform` and `Binder.expandTemplatesIn` make of the subtrees they pass through (#2464, #2526). `PlanMemo` finds a node by identity, then among the copies its caller recorded, by value at the same span. `sharedScans` records the expanded copies with `match_copied_subquery_scans`; the other node-keyed memo tables (`scalarResults`, `correlatedSubqueries`, ...) are still identity maps.
- `WvletEngine.runtimePlan` uses a new `Planner` per call; share one `Planner` when building plans by hand in tests.

| Phase | Where |
| --- | --- |
| Plan setup | `Planner.plan` / `planRoot`: shared subqueries and scans (`SharedScans`, `DuplicateSubqueries`), scalar prefetch, sources (`catalog/`) |
| Binding | `RuntimeBinder`, `Binder` (`plan/BoundExprSimplifier.scala`), and the `Planner` traits it calls |
| Logical passes | `Optimizer` over the `RuntimePlan` (`runtime/`) |
| Estimates and join order | `Stats` over the `RuntimePlan`, `CardinalityEstimator` (shared formulas), `JoinEnumerator`, `JoinOrderOptimizer` |
| Shared CTEs and replanning | `plan/SharedResults.scala` (`DeferredCTE`, `finalizeCTEs`), `runtime/CTEJoinKeys.scala`, `Planner.replanRuntime` |
| Lowering and physical steps | `Lowering`, `plan/PhysicalSteps.scala` (`optimizePhysical`), `Parallelizer` |

- `Optimization`'s cases are grouped by these phases; the notes below follow the same groups.

### Plan setup

- A folder (or glob) of plain Parquet files is read as its files' single-file `ParquetSource`s (`catalog/ParquetFolder.scala`, `folder_file_scans`): splits per row group of every file, source row filters, and row counts, ranges, distinct counts and samples merged from the files. Only when every file reads as a single file with the folder's columns and types, and the folder has no partition folders, Iceberg or Delta metadata; anything else stays on uni's dataset reader, which applies partition values, schema evolution and deletes. A catalog source re-lists its folder at most once a second (`ParquetSource.VersionRecheckNanos`) and reopens files only when the (path, size) listing changed. The toggle is applied in `Planner.tableSource`/`fileSource` (`ParquetSource.withoutFolderFiles`), since engines share catalog sources. Hive-partitioned folders (`key=value/`) are read as their files too: `ParquetSource.openDataset` types integer and `yyyy-MM-dd` keys as BIGINT and DATE (DuckDB's `hive_types_autocast`; cached per path so that a folder is listed once per open), uni's dataset (kept with the listing) picks a scan's files by their partition values, each file is read as a single file without the filter's partition-key conjuncts, and the partition values are added as constant columns. With `partition_row_filters` (applied as `ParquetSource.withoutPartitionRowFilters`), a partitioned folder read as its files takes a source row filter: `ParquetFolder.decideKeys` decides its partition-key leaves by each file's values (a NULL value passes only `IS NULL`), skips the files it rejects, and gives each file the rest over its own columns; a scan of only partition keys reads the columns the rest tests. With `partition_probe_scan_cost` (and `key_set_row_groups`), the exact join search (`JoinEnumerator.partitionReads`) credits a join whose build keys reach a probe scan's partition key (`Stats.partitionKey`: at least two parts, each holding one value, on a source that skips parts by key sets) with the rows of the parts it skips, the build keys' share of the key's values, once per input at its smallest share. Runtime join filters on other keys cost no reads in the search, so without the credit TPC-DS q25 over date partitions built store_sales and probed it with its 30 dates. A large folder is re-listed after `FolderRecheckFactor` (50) times its listing time.
- Local Iceberg tables and schema-evolved folders are read file by file too (`dataset_file_scans`). An Iceberg table (`catalog/DatasetFiles.scala`) splits into the data files uni's `selectFiles` keeps (partition values and manifest statistics), each read through `ParquetDataset.withFiles(Seq(file))` so uni still applies deletes, field-ID column mapping and defaults; it takes exact row filters (uni filters each file), and planning reads row counts, int/date ranges and per-file part ranges from manifest statistics. It is reopened on every re-list (deletes can change without the file list changing), and its parts carry no row counts. When every data file of a table reads as a plain Parquet file (uni's `ParquetDataset.readsAsPlainFile`: no deletes, renames, dropped columns or defaults, and its partition columns stored in the file), the table is read as a `ParquetFolder` instead (`iceberg_row_groups`): it splits by row group, takes source row filters during decode when every file holds all of the table's columns (otherwise it reads like a schema-evolved folder), and is still reopened on every re-list. A folder whose files hold only some of its columns (same types) stays a `ParquetFolder`: it splits like a partitioned folder, reads a file's missing columns as NULL constants, drops filter conjuncts on them for that file, and has no source row filter. Folders with widened types stay on uni's dataset reader.

### Binding

- The binder simplifies each expression as it binds it (`plan/BoundExprSimplifier.scala`), before the logical passes: `fold_bound_constants` turns nodes over literals into literals (so `x <= 1200 + 11` reaches scan filters) and simplifies `and`/`or` with a literal operand; `unwrap_casts` compares `x` instead of `cast(x as T)` with literals when the cast is lossless (integer widening, integer or decimal to a wide enough decimal) and every literal converts exactly; `round_unwrapped_literals` also unwraps a cast that only adds fraction digits (`cast(x as decimal(38,12)) > 81029137.652468`, TPC-H q11's HAVING), comparing x with the literal rounded to x's scale (down for `>`/`<=`, up for `>=`/`<`; equality only when exact). A failing evaluation (`1 / 0`) stays unfolded, so it still fails only when rows exist.

### Logical passes

- `group_key_semi_joins` also reduces an aggregation on the left of an inner join by swapping the inputs with the same build side (`left_group_key_semi_joins`), so the copy of the semi-join source is lowered after the original.
- `aggregate_windows` (`runtime/AggregateWindows.scala`, right after `group_key_semi_joins`) turns a join with a per-key min, max, or avg of the same rows (a decorrelated scalar subquery, TPC-H q2/q17, TPC-DS q32/q92) into a window over the join, so the table is read once. It applies only when the outer rows are the aggregation's input joined with other relations on the group key alone; sums and counts scale with the join's fan-out and are left. Modeled in `formal/WvletFormal/AggregateWindows/`.
- `eager_aggregation` (`runtime/EagerAggregation.scala`) computes an aggregation below the top inner join under it, by the aggregated side's join keys and the group-key columns it holds, when the calls read one side and can't fail on rows the join drops (sum, min, max and counts over columns, `+ - *`, division by a nonzero constant, widening casts), the partial groups are at most 1/4 of that side's `Stats.treeRows` and at most 4x the outer groups (partial groups estimated over clusters with `clustered_group_estimates`, below), and the other side keeps ≥ 70% of its rows. Shared CTE bodies run it again in `SharedCTE.lower` once their readers' filters are pushed in (TPC-DS q04, q11). With `eager_other_side_min_max`, calls that are filter-free mins or maxes of the other side's columns stay in the outer aggregation, and the other side may be a cross join with a one-row side (a keyless aggregation under projections) (TPC-DS q23's best customers).
- `eager_aggregation_in_join_trees` (in `EagerAggregation`, when the top-join rewrite doesn't fire): descends inner hash joins, filters and plain-copy projections under the aggregation to the input the calls read, and pre-aggregates it by the columns read above it. Only when every join on the path looks up one row of its other side by a declared unique key (`DependentGroupKeys.uniqueOn`), its other side supplies a column the aggregation reads and keeps ≥ 70% of its rows, the join keeps ≥ 70% of the input (`Stats.treeRows`), every filter keeps ≥ 70%, and the outer keys determine the pre-aggregation's keys (`DependentGroupKeys.determines`): each outer group is then one joined row, so the outer aggregation becomes a projection, and a 1.5x reduction suffices. TPC-H q10 sums order lines per `o_custkey` before the customer and nation lookups. Merging partials under non-lookup joins (TPC-DS q04's CTE bodies) ran 1.07x slower at SF10 and isn't done.
- `eager_distinct` (in `EagerAggregation`): a DISTINCT (the `Distinct` node, or an aggregation without calls) over a deterministic projection of an inner join inlines the projection into its keys and runs the top-join rewrite, so a side of the join is deduplicated by the columns the keys and join keys read, under the same guards. The outer distinct stays over the join, so the result is the distinct projected rows, not the distinct join keys. TPC-DS q38 and q87 dedupe 5.4M store sales rows to 481K `(customer_sk, d_date)` pairs at SF10 before joining the customer names.
- `eager_lookup_projection` (in `EagerAggregation`'s top-join rewrite): when the join's other side is unique on its join keys (`DependentGroupKeys.looksUp`), every call is computed before the join, and the group keys determine the partial groups (`DependentGroupKeys.determines`), the outer aggregation is a projection of the partial results, since each outer group is one joined row. TPC-DS q04, q11 and q74 no longer regroup their per-customer-key sums by `c_customer_id`.
- `dependent_group_keys` (`DependentGroupKeys`, after `EagerAggregation`): an aggregation groups only by the keys that determine its others. Known columns come from plain-column keys, inner hash join equalities, and every column of a table once one of its declared unique keys is known; columns are traced through filters, deterministic projections, inner joins and the preserved side of outer, semi and anti joins, never a NULL-padded side. Dropped keys become `any_value` calls (split in two phases like min/max), which `PruneColumns` drops when nothing reads them. TPC-H q10 groups by `c_custkey` alone, q3 by `l_orderkey`, q18 by `o_orderkey`; TPC-DS q23's `frequent_ss_items` no longer reads `i_item_desc`.
- `dimension_group_ids` (`DimensionGroupIds`, after `DependentGroupKeys`): an aggregation whose string group keys are columns of a dimension (a scan under filters and projections) that an inner hash join looks up by its declared unique integer key groups by `rep = min(key) over (partition by those strings)`, computed by a window over the dimension, and joins the strings back per group from a copy of the dimension grouped by them (the same `min(key)`). The dimension must be a scan under deterministic filters and projections, so the copy reads the same rows. It fires when the looking-up input is ≥ 8x the dimension's estimated rows and isn't an aggregation's output, the strings are read by nothing but the group keys, and they are coarse (estimated groups ≤ 1/4 of the dimension's rows, or the dimension has ≤ 1,000 rows). TPC-DS q47, q57, q62, q66, q89 and q99 group by reps.
- `late_columns` (`LateColumns`, before `PruneColumns`): under a sort with a limit N, the string columns of a scan that reach the sort as plain copies only (no filter, join key, computed projection or sort key reads them) are read back for the N rows alone: the top-N is computed without them, and a hash join probing a second scan of the table (its declared unique key and those strings) with the N rows on that key restores them, under a sort that restores the order. Each key column must reach the sort and be read by an inner join on the way, so none is NULL and each of the N rows finds the one row it came from; the N keys filter the second scan per row and skip its row groups that hold none (`key_set_row_groups`). It fires when the rows estimated at the sort are ≥ 64 N and ≥ 1/16 of the table's rows. TPC-H q10 decodes the name, address, phone and comment of its top 20 customers instead of 381K (0.94x wall at SF10); the second scan still decompresses the string pages of most row groups (one page per row group).

### Estimates and join order

- With `or_equals_selectivity`, `x = a or x = b` (also with `x in (...)` disjuncts) over one expression keeps n / ndv of the rows, as `x in (a, b)` does, instead of the default 0.3.
- Semi / anti joins of EXISTS / IN subqueries build on the outer input (RIGHT SEMI / RIGHT ANTI) whenever the subquery input is estimated larger (`semi_join_build_side`); inner and outer joins swap only at 4x (`JoinOrderOptimizer.SwapBuildRatio`). A subquery that aggregates or deduplicates keeps the 4x rule, as row estimates pass through filters and aggregations (`CardinalityEstimator.rows`, `Stats.rows`); lineitem vs orders thus compare at their source ratio.
- The join search estimates a range comparison of an integer or date column with constants (`<`, `>`, `between`, date ranges) from the column's [min, max] in the Parquet footer, with the bounds on one column as one interval (`range_selectivity`, `runtime/RangeSelectivity.scala`); decimals have no footer range in uni and keep the default 0.3. `Stats.rows` and `CardinalityEstimator.rows` still pass source rows through filters and joins, so build-side choices outside the join search (semi joins, and the semi joins `reduce_semi_joins` and `group_key_semi_joins` add) don't see these estimates; `group_key_semi_joins` does read them for the size of its semi-join source.
- With `smaller_outer_builds` (needs `parallel_outer_tail`), an outer join builds on its preserved side once the other side is estimated 2x larger (`JoinOrderOptimizer.SwapOuterBuildRatio`) instead of 4x; the build's keys then filter the larger input's scan, as DuckDB's dynamic filters do. A shared CTE body chooses its outer build sides again once its readers' filters are pushed into it (`ReorderJoins.outerBuilds`; TPC-DS q75 builds on the date-filtered sales and probes the returns).
- `clustered_group_estimates` (`runtime/ClusteredGroups.scala`) estimates an aggregation's groups in `Stats.treeRows` and the eager-aggregation guard as D (1 - e^(-(R / r) / D)) for R rows over D key combinations in clusters of r rows (Cardenas' formula over clusters), where r is the shortest sampled run (`TableSource.keyRunLength`) among the keys and the columns that select the rows on the probe path (filter columns, inner/semi/anti probe keys, residuals). A build-side key column of a join on a unique build key runs as long as the probe keys. Runs below 2 or unknown keep min(D, R). TPC-DS order lines share customer and date (run 11.9 in web_sales), so q74's web (customer, year) groups estimate 214K for 212,810 real instead of 1M.
- `nested_group_estimates` (`Stats.treeRows`): an aggregation over another aggregation reads its keys' distinct values through the inner grouping keys, which keep their input columns' distinct values, instead of taking the inner aggregation's rows. Only the group estimate traces through groups; declared-key coverage does not, as grouping makes keys unique. TPC-DS q65's average by store over sums by (store, item) estimates the store count (102 at SF10) instead of 5.8M, so the join builds on it (0.80x wall at SF10).
- `rank_filter_rows` (`runtime/RankFilterRows.scala`, in `ReorderJoins.orderTree`): an inner-join input that filters a `row_number()` or `rank()` with ORDER BY by a constant (`rnk < 11`, `<=`, `=`, or a BETWEEN) is estimated as at most N rows per window partition (the PARTITION BY keys' distinct values; N overall without PARTITION BY), when that is below its other estimates. `rank()` can keep more than N rows on ties at the bound; `dense_rank()` is not bounded. It shares `WindowOp.rankBound` with `window_top_n`, so the estimate and the runtime top-N read the same filters. `Stats.rows` and `Stats.treeRows` do not apply it. TPC-DS q44 builds on its two top-10 rankings at SF10, and the item scans probe them (0.91–0.96x wall at SF10).
- `key_join_estimates` (`Stats.keyCoverage`, `CardinalityEstimator.compositeDivisor`): an equi-join on several columns, each side tracing to one scan, reads the unique keys the scans' tables declare (`TableSource.uniqueKeys`: warehouse `create table` specs, `EngineCatalog.registerParquet(name, path, uniqueKeys)`, sidecar key files of Parquet data (`catalog/TableKeys.scala`: `<name>.keys.json`, or `_keys.json` in a folder, local paths only), generated TPC-H and TPC-DS tables, and `catalog/BenchmarkKeys` for the TPC harnesses). Covering a declared key of a side of B base rows divides by B (foreign key to primary key); covering none, with both tables declaring keys, divides by every pair without the max(|L|, |R|) cap of correlated keys (TPC-DS q25's catalog_sales ⋈ store_returns on item and customer). Otherwise the estimate is unchanged. See [the declared unique keys ADR](../adr/2026-11-25-engine-declared-unique-keys.md).
- `probe_scan_cost` (`JoinEnumerator`): the exact join search adds, for each join whose probe side is one input, the probe rows its build's runtime filters are expected to keep: probe rows × the smallest ratio over the keys of build to probe distinct values, a build key's distinct values capped by the rows of every join in the build's tree that holds its input (inner joins add no key values; TPC-DS q72's date_dim joined by week stays at the item key's rows). It makes q25 join catalog_sales with its date filter before store_returns, which `key_join_estimates` alone ordered after (a 1.35x regression); probes that are joins are charged only with `join_probe_scan_cost`.
- `join_probe_scan_cost` (`JoinEnumerator`): with `probe_scan_cost`, a probe side that is a join pays the same charge, its output rows times the pass rate, each probe key's distinct values capped by the rows of the probe tree's joins holding its input. Without it, the search built on a large single input so that it paid no probe charge: TPC-H q10 built on customer and its seven grouped columns instead of probing it with the filtered order lines.
- `implied_join_equalities` (`ReorderJoins.withImpliedEqualities`, `JoinEnumerator`): the column equalities of an inner join tree form equivalence classes (three or more columns of one type, each on a different input), and every two columns of a class get an `implied` edge, so the exact search may join any two of their inputs directly. The search estimates a join's keys of one class as one key (each side by its fewest distinct values) and the tree keys each join on one pair per class; the others hold through the equalities below it. When the implied edges make a class a clique of more pairs than `JoinEnumerator.PairBudget`, the exact search runs again over the written edges only; the greedy fallback also sees only those. TPC-H q5 (`c_nationkey = s_nationkey = n_nationkey`) now joins customer to nation and region first, as DuckDB does.

### Shared CTEs and replanning

- `cte_determining_join_keys` (`runtime/CTEJoinKeys.scala`, run by `Planner.planRoot` on the bound plan): an equality of two readers of one shared CTE (a top-level inner-joins condition) on a string column that copies a single-column declared unique key becomes an equality on a long declared key of the same table, plus `is not null` on the string key. The CTE body gets the long key as one more output column (and group key; `dependent_group_keys` then groups by it alone) when it traces through projections, filters, preserved join inputs, group keys and same-table union branches, and an inner equi-join on it shows it is non-NULL; the body is optimized again. Readers bound earlier read the columns before it (`SharedCTE.readerSchema`). TPC-DS q04, q11 and q74 join their `year_total` readers on `c_customer_sk`.
- `cte_filters_through_filters`: the readers' filters pushed into a shared CTE body (`Optimizer.pushFilters`) move below the body's own filters when `Selection.isSafe` says they can't throw, so they reach the joins and scans under them (TPC-DS q64: `syear in (1999, 2000)` below the `cd_marital_status <>` filter, down to `date_dim`). Conjuncts that can throw stay above.

### Physical: scans and filters

- Scan filters (`plan/ScanFilters.scala`, `push_scan_filters`) only skip Parquet row groups, so a translation must keep every row group the engine's own comparison could keep. With `decimal_float_scan_filters` they also compare decimals (checked by `catalog/DecimalStats.scala` for single-file scans, since uni treats DECIMAL statistics as always matching) and floating-point `<`, `<=`, `=`; never `>` or `>=` on floats, because the engine orders NaN above every number (`Double.compare`) and writers leave NaN out of the statistics.
- `FilterOp` evaluates an AND / OR condition with `expr/Selection.scala` (`short_circuit_filters`): each conjunct runs only on the rows the earlier ones kept, each disjunct only on rows not yet accepted, so a costly conjunct (string IN, LIKE, a function) is not evaluated on rows already removed. Filters with cheap parts only keep the full-batch masks, and cheap leaves run over the whole batch, so a failing cast may still see removed rows, as before. `reorder_conjuncts` runs cheap parts first by a static cost; a part that can throw (`Selection.isSafe` is false) is a barrier no part moves across, so it never sees more rows than in the written order. With `dictionary_selection`, a part over one dictionary-coded string column (`dictionary_filters`, now also a whole AND / OR over that column) runs once per dictionary entry of the rows still selected and returns their positions (`Selection.DictLeaf`), and an AND with two such parts selects even though every part is cheap (TPC-DS q41). Elsewhere (projections, CASE, join residuals) AND / OR still evaluate both sides over the whole batch.
- Per-row runtime join filters (`exec/RowKeyFilter.scala`) over a bitmap or a Bloom filter of at most `RowKeyFilter.MaxSortedKeys` build rows (which keeps its keys sorted) also go into a Parquet probe scan's row-group filter as `In` over `RowKeyFilter.prunedSet` (`key_set_row_groups`): uni skips a row group whose [min, max] holds no build key, not only those outside the keys' range. TPC-DS store_sales is clustered by ticket number, so the ~15 tickets of q17's and q25's catalog_sales ⋈ store_returns build hit a few of its 236 SF10 row groups, as DuckDB's IN-list dynamic filters do. The filters only skip row groups; rows are still tested as before. Sources opt in with `TableSource.supportsKeySetRowGroups`: `ParquetSource` does for folders and Iceberg tables too, whose row filters uni tests after decoding, since uni's dataset applies the row-group filter to each file's row groups.
- A pipeline scan of a single Parquet file that reads one row group (no parts, so `MorselOp` runs it on one thread) gets the pipeline's runner (`ScanSpec.decodeRunner`, `parallel_column_decode`): with no row filter, it decodes the row group's columns as tasks of `TaskRunner.inParallel` (the calling thread takes the first), so every column holds the same rows. `ParquetSource.decodeTasks` groups the columns into tasks of at least `ParallelDecodeMinBytes` (2 MB uncompressed, from the column chunk metadata); when that leaves one task, the scan reads as before (`readBatches`). Smaller tasks cost more CPU than they saved: one task per column of TPC-DS item's three small q06 columns took 8% more CPU. A scan with a row filter decodes on one thread, because the filter picks the rows that every column decodes. TPC-H supplier is a single 100K-row row group at SF10, and q2's supplier join build decoded its string columns for ~20 ms while the other threads waited.
- With `plain_string_bytes`, a Parquet string column without a dictionary (PLAIN pages) is held as uni's UTF-8 bytes and offsets (`StrVec.ofBytes`), shared and not copied, instead of one String per row (about 76 B for a 28-byte value against 32 B). LIKE patterns made of literal fragments and `%` match the bytes (`expr/LikeBytes.scala`), so a column read only by such a filter never builds Strings (TPC-H q13's `o_comment`). A gather is a view that shares the source's bytes through a row index, so a join's fan-out doesn't copy a dimension's bytes per output row. Other readers build the Strings once per source vector (`StrVec.values`), views share them, and a vector drops its bytes once its Strings are built. Until then a view keeps its source page's bytes alive. `parallel_string_decode` does not apply to these columns. Why not off-heap `Canvas` buffers: see [the ADR](../adr/2026-11-27-engine-plain-string-bytes.md).

### Physical: joins

- With `parallelize`, INTERSECT / EXCEPT (without ALL) become semi / anti hash joins over the left input's distinct rows on every column, with NULL keys equal (`set_op_joins`, `HashJoinOp.nullsEqual`). A build with a NULL key skips the packed, direct, and flat paths; a join with NULL-equal keys takes no runtime filters. `Parallelizer` creates these joins after the planner's join passes, so it calls the planner's `configureJoin` on each one. That way the join toggles, and `probe_miss_filter` for the anti joins, reach them too.
- With `unmatched_left_probe` (`Planner.markUnmatchedLeftProbes`, after column pruning), a LEFT hash join without a residual, under a filter with a conjunct `k is null` for one of its build key columns, emits only its unmatched probe rows in probe order with NULL build columns (`exec/ProbeRows.scala`): a matched row's key equals a non-NULL probe key, so the filter drops every matched pair. With `probe_miss_filter`, such joins and anti joins give a flat `LongJoinTable` of at least `LongJoinTable.MinMissFilterBytes` of entries a Bloom filter of its keys (about 8 bits per key, split by the table's partitions) that each probe checks before the entries. TPC-DS q78 keeps its sales rows without a return this way.
- A flat `LongJoinTable` entry is one Long, `(key - min) << rowBits | row`, when the build keys span fewer than 2^(64 - rowBits) values; otherwise it is two Longs. With `narrow_join_entries`, `rowBits` is the fewest bits that hold every build row (`64 - nlz(buildSize)`); without it, 32. Entries stay exact, and the row field is never all ones, so -1 still marks an empty entry ([ADR](../adr/2026-11-26-engine-narrow-join-entries.md)).
- `semi_anti_one_probe` (`runtime/SemiAntiProbe.scala`, matched in `Lowering`) runs an anti join over a semi join of the same table on the same keys (or the other nesting), both building on the outer rows, as one RIGHT SEMI hash join that probes the table once: each probe row marks build rows matched by the EXISTS's condition and excluded by the NOT EXISTS's (`HashJoinOp`'s `exclude`, `exec/BuildExclusions.scala`). TPC-H q21 reads lineitem twice instead of three times. The probe reads both scans' columns and the OR of their row-group filters. The Lean model is `formal/WvletFormal/SemiAntiProbe/` ([ADR](../adr/2026-11-26-engine-semi-anti-one-probe.md)).
- With `parallel_outer_tail`, a right / full join's unmatched build rows, emitted after every probe part (the `MorselOp` tail), are emitted by tasks over disjoint ranges of the build rows when the pipeline has one such join and the build has at least `MorselOp.MinTailSplitRows` rows; each range runs through its own copy of the operators above the join. A UNION ALL input with such joins also joins the union's pipeline, its tail running after every part of the union, so `union_distinct_once` still applies. Nested right / full joins keep one run of the tail.

### Physical: aggregation

- Two-phase aggregation merges identical partial aggregates (`shared_agg_partials`), so `avg(x)` reuses `sum(x)` and `count(x)`.
- With `aggregate_selected_rows`, `HashAggOp` reads deferred input columns (a filter's or join probe's `Batch.take` output) at their positions instead of gathering them (`exec/SelectedInputs.scala`): sum / min / max / count over an Int64, Double, or Long-backed decimal column (`Accumulator.updateSelected`), `+` / `-` trees over such columns into one array (a decimal Long overflow evaluates the tree as before; Int64 overflow throws as before), and packed group keys (`PackedGroupTable.groupIdsAt`). Position -1 reads as NULL. With `fused_accumulators`, arguments are evaluated up front only for batches the fused loop folds. Other aggregates (FILTER, DISTINCT, several arguments) gather as before. Fused decimal `x * (c ± y)` products (`fused_decimal_arith`) read their column operands in place too.
- With `column_major_fused_sums`, the fused fold of `fused_accumulators` adds one sum at a time into four lanes per group (`exec/ColumnMajorSums.scala`). The batch's sums skip the per-row overflow check when the OR of the values' magnitudes bounds them within a Long; otherwise they add row by row with the check.
- With `agg_scratch_buffers`, `HashAggOp` over dense selected rows computes fused decimal products into Long arrays reused from batch to batch (`expr/LongScratch.scala`, reset before each batch's fold), and one or two string keys with dictionary codes take their group ids in one pass into an id array the `GroupTable` reuses (`exec/DictionaryIdsAt.scala`). This holds only because aggregations read their arguments and group ids while folding the batch; a reader that keeps a vector past the batch must not take scratch arrays.
- With `long_group_tables`, a hash aggregation over one Int64-backed key (the packed key of `PackedGroupTable` and of `PartitionedAggOp`'s partitions, or a single Int64 / timestamp key) groups through `exec/LongGroupTable.scala`: 4-byte group-id slots, the key compared from the group's key array, hashes recomputed from the keys instead of stored, and NULL as one group outside the slots. Group ids and their order are the same as a `GroupTable` gives. Interleaving each key with its group id in 16-byte slots was slower (TPC-DS q97 CPU +6% at SF10): the near-unique final stages touch twice the memory per probe.
- With `sorted_group_runs`, a `LongGroupTable` starts without slots and gives consecutive equal keys one group while the keys come non-decreasing with no NULL, so a partial aggregation over a scan sorted by its key (TPC-H lineitem by `l_orderkey`) assigns group ids with one comparison per row. The first key below the last group's, or the first NULL, inserts the groups so far into slots and hashes the rest, with the same group ids. `MorselOp` emits the partials in part order and partition routing keeps their order, so the final partitions of a two-phase aggregation over such a scan keep the runs too (TPC-H q18's IN subquery, 0.68x at SF10).
- With `sorted_agg_splits`, a `PartitionedAggOp` whose input is non-decreasing in one integer grouping key with no NULL (checked per batch at run time) cuts the batches at key changes into contiguous runs (`exec/SortedAggSplits.scala`) and aggregates each run as a partition, skipping hash routing. A run ends only between batches whose boundary keys differ, so groups stay whole; a key that cuts fewer than half the partition count of runs falls back to hashing. Its output is in key order. On TPC-H q18 the final aggregation's CPU drops about 20-40% (5-9% of the query).
- With `packed_agg_routing`, a hash-routed `PartitionedAggOp` whose keys are columns that pack into one Int64 (`AggKeyPacking`) takes the key ranges over its whole input in the routing tasks, packs each batch's keys while routing, partitions rows by the packed key's hash, and copies only the packed key and the columns its aggregates read into the partitions (the key columns stay deferred and unread). Partitions group by the packed key without packing again. Reading partition rows in place at their positions instead of copying them was slower (TPC-DS q78 CPU +26% at SF10): every pass over scattered positions pays the cache misses that one gather pays once.
- With `size_partitions_by_rows`, a `PartitionedAggOp` whose group estimate reached `GroupTable.MaxPresizeGroups` sizes each partition's group table and aggregate state for the partition's row count (an upper bound on its groups), up to `MaxPresizeGroups` per partition. An even share of the capped estimate sized TPC-DS q97's and q78's SF10 partitions for 4096 groups while they held ~50K, so each table rehashed about four times. The per-partition cap bounds the zero-filled memory of an overestimate, for example when the partials grouped well; on the single-thread path the sizing is unchanged.

### Physical: expressions and deferred columns

- `Lowering` rewrites expressions over positions, after the logical passes: `fold_constants` folds row-independent subexpressions and pre-scales decimal constants, and `common_subexpressions` computes a subexpression repeated across a Project, Filter, Aggregate, or Window once in a Project below it (`CommonSubexpressions`). It shares only subexpressions evaluated for every row in at least one place, never volatile functions, and matches with `==`, not `sig`.
- With `fused_decimal_arith`, lowering (`runtime/FuseDecimalArith.scala`) turns decimal `x * (c ± y)` for a constant c into `expr/FusedDecimalMul.scala`, which prints as the `Arith` it replaces (no plan change) and computes the product over unscaled Longs in one loop. It divides to check overflow only when an operand is outside the Int range; a Long overflow evaluates as `Kernels.arith` does.
- With `dense_selected_rows`, `ProjectOp` passes a deferred input's columns through still deferred, and `ProjectOp` and `HashAggOp` compute expressions over a filter's source rows when every column they read is deferred at the same positions and at least half the source rows are kept (`exec/DenseSelectedRows.scala`). Only expressions that cannot fail on a dropped row qualify: column references, constants, and decimal / double `+` / `-` / `*`. Int64 arithmetic, division, casts and functions are computed over the kept rows as before. The result is deferred at the same positions. Fused accumulators then read their arguments at those positions when every argument qualifies and no position is -1, and string group keys with dictionary codes look up the codes there (`GroupTable.groupIdsAt`).
- With `deferred_null_checks`, IS NULL of a column a join or filter output has not gathered yet reads the column's positions (-1 for an outer join's padded rows) and its source's nulls instead of gathering it (`expr/DeferredNullChecks.scala`, TPC-DS q97's null checks over the FULL join output). Other readers of the column still gather it on their first read.

### Physical: parallel execution

- With `parallelize`, a UNION ALL of scan pipelines is one pipeline (`union_all_pipelines`): one `MorselOp` runs the parts of every input, in input order and then part order, through the operators above the union (hash join probes over one shared build, partial aggregates). An input whose source has a single part runs on the calling thread in its turn; a union with an input that is no pipeline, or has right / full joins, keeps its inputs' own pipelines.
- With `union_distinct_once`, UNION (distinct) flattens nested UNION (distinct) inputs of the same column types and, when the flattened union is one pipeline (so it needs `union_all_pipelines`), runs one two-phase distinct over it: a partial per scan part and one final partitioned aggregation, as DuckDB does. Otherwise each input is reduced to its distinct rows before the final one (TPC-DS q75, 0.73x at SF10).

## Optimizer toggles

- `Optimization` (`plan/OptimizerOptions.scala`) names each planner optimization. Turn them off with `wvlet.engine.optimizer.disabled=<names>`, `WVLET_ENGINE_OPTIMIZER_DISABLED`, or `WvletEngine(optimizer = ...)`.
- `EngineOptimizerToggleTest` checks results with each optimization off, and that each one changes some TPC-H or TPC-DS plan. It compiles the queries and runs DuckDB once for all toggles, so a new toggle costs only the engine runs. A toggle that changes no plan (a runtime-only change) needs an entry with its reason in `noPlanChange`.
- `Optimization`'s cases are grouped by the phase that reads them (plan setup, binding, logical passes, estimates and join order, shared CTEs and replanning, then physical scans, joins, aggregation, windows, expressions, and parallel execution, then execution-time resource accounting). A new toggle goes at the end of its phase's group, and at the same position in `OptimizerOptionsTest`'s name list, or the JS and Native CI jobs fail.
- Give every executor or planner change an `Optimization` toggle from the start, so it can be benchmarked on one build. A refactor that leaves every golden plan identical needs none; benchmark it against an origin/main worktree ([ADR](../adr/2026-11-27-engine-optimizer-structure.md)).
- Operator flags set after lowering are mutable fields, and Parallelizer rebuilds operators. A new `HashJoinOp` or `JoinBuild` flag is copied in `withFlagsOf` (`exec/JoinFlags.scala`); `EngineJoinFlagsTest` finds the public Boolean flags by reflection and fails when `withFlagsOf` or one of Parallelizer's two join rebuilds drops one; a new rebuild site must call `withFlagsOf` too.

## Parquet footer cache

- `ParquetFooterCache` (`catalog/`) keeps parsed footers of local Parquet files, process-wide, LRU up to 256 files. Behind `parquet_footer_cache` (on by default).
- An entry is valid while the file's size and last-modified time match a stat taken before the footer read. Symbolic links, files without an mtime, and files modified within the last 10 seconds are not cached, as DuckDB's `parquet_metadata_cache` does for coarse mtimes.
- Scans use it when `ScanSpec.footerCache` is set (from the toggle at lowering); planning reads when the `ParquetSource` was built with `footerCache` (file paths in queries). Other callers parse as before.
- `ParquetSource.estimatedDistinct` caches estimates per (path, column) with the file version from the same stat helper (`ParquetFooterCache.fileVersion`), LRU up to 4096 entries. `ParquetSource.valueCounts` (string value samples from up to 4 row groups, for `string_value_selectivity`) caches the same way in its own LRU of 512 entries. `ParquetSource.keyRunLength` (the mean run of equal consecutive values in the same sampled row groups, for integer, date and string columns) shares the distinct-count LRU. A changed version recomputes; files the footer cache skips are estimated once per `ParquetSource` (one query), not shared. It validates with or without the toggle. A source reads the file version at most once per second (`ParquetSource.VersionRecheckNanos`): join ordering asks for estimates thousands of times per query, and a stat per call took most of TPC-DS q64's planning time.
- Only local paths are cached. A remote source would need a key that changes on overwrite (e.g. an ETag), since uni's `FileInfo` has none. See [the footer cache ADR](../adr/2026-11-24-engine-parquet-footer-cache.md).

## Memory accounting

- Each `WvletEngine.execute` call opens a `MemoryContext` (`exec/MemoryContext.scala`) that reserves bytes from the engine's `MemoryPool`, by default `MemoryPool.process` (unbounded until a server sets its own), with the pool's `queryLimitBytes` unless the engine sets `queryMemoryLimit`. Behind `memory_accounting` (on by default); off, every operator gets `MemoryContext.NoOp`.
- Only large holders reserve, from estimated vector sizes (primitive widths, sampled string lengths, or the bytes plus 4 bytes of offset per row of strings held as bytes): join builds per drained build batch plus 12 bytes per row for chains and tables; hash aggregations per group (key and state widths plus 12 bytes for the table) through `MemoryContext.growing`, which reserves a quarter of the size (at least 64 KB) ahead; partitioned aggregation inputs; sort and window inputs (a streaming window top-N only its kept rows); shared CTE results; `DistinctOp` tables, INTERSECT / EXCEPT key maps, and nested-loop (and parallel cross join) build rows; and result batches as `execute` drains them. Morsel parts (`MorselOp.runPart`) build their pipelines under `NoOp`: a part's partial tables are dropped once drained and bounded by the part, so holding their reservations until the query ends would overcount.
- A holder reserves through its own `MemoryContext.child()` and calls `release()` once it drops its buffer, so its bytes return before the query ends: sorts, windows, and aggregations after emitting their last batch, distincts and nested-loop joins once their input is done, set operations on return, and join builds once every probe finished. A join probing its build alone frees it at its end; a parallelized join's build is freed by its `MorselOp`'s `done` hooks (`Parallelizer`'s `Pipeline.done`) after the last part and tail, and its copies never free it. Freeing drops the tables (`JoinBuild.free`) only while memory is tracked, so `memory_accounting` off keeps them to the query's end. The context keeps its peak (`peakBytes`, counting early releases), which the benches report as `engine_peak_mb`.
- Everything else, including shared CTE results, stays reserved until `execute` returns, and is released in one outer `finally`, on success and failure. Releases after the query closed return nothing.
- A pool with a `killDelay` kills the query holding the most bytes once it has stayed over capacity that long with more than one context open (`killLargestIfStillOver`). The engine has no interrupt checks, so a killed context fails where the engine regains control: its next reservation, `MorselOp` part, or result batch (`MemoryContext.checkKilled`). A killed query that holds without reserving and runs no morsels fails at its first result batch.
- An `OutOfMemoryError` thrown while `execute` plans or runs becomes RESOURCE_EXHAUSTED (`MemoryContext.outOfHeap`) after the operators are closed and the context released, naming the query's peak tracked memory and how to raise the heap (`-Xmx`, `GC_MAXIMUM_HEAP_SIZE`) or, on a server, set `--max-query-memory`. `NonFatal` never matches it, so plan-time fallbacks don't swallow it.
- Past `queryMemoryLimit`, the reserving call throws RESOURCE_EXHAUSTED. Plan-time fallbacks that catch `NonFatal` must rethrow it (`MemoryContext.exceededLimit`). The pool's capacity is soft: reservations past it succeed, and `isOverCapacity` is for admission checks.
- Operators capture `MemoryContext.current` at construction instead of taking it as a parameter. `execute` sets it before planning, and `Planner.plan`, `lower`, and `physical` re-enter the planner's context, so plans built later on a worker thread capture it too. An operator that builds operators at run time (outside the planner) must pass its own context on, as `PartitionedAggOp` does for its partitions' `HashAggOp`s. Server worker threads are reused, so the context is restored after each scope.

## Spilling

- A query can spill once its `MemoryContext` has a spill threshold (`withSpill`, set by `WvletEngine.execute`): `WvletEngine.withSpillThreshold`, by default the smaller of the query limit and `SpillCompat.defaultThresholdBytes` (half of `Runtime.maxMemory` on the JVM, or the bytes of the `wvlet.engine.spillThreshold` system property; none on Native, whose heap has no default cap, and on Scala.js, which has no files). See [the spill framework ADR](../adr/2026-11-27-engine-spill-framework.md).
- Spillable holders call `tryReserve(bytes)`: false, reserving nothing, when the query would pass its threshold; the holder then spills and releases its child context. Without a threshold, and on `MemoryContext.NoOp` (morsel parts, `memory_accounting` off), it is `reserve`. Pool pressure is not a trigger: the pool's capacity stays soft, for admission and the low-memory killer.
- Spill files live in a per-query folder `wvlet-spill-<random>/` under `WvletEngine.withSpillDirectory` (default `java.io.tmpdir`), owner-only, created on the first spill (`MemoryContext.spillSpace`, `FileSpillSpace` in `wvlet-engine/jvm-native`) and deleted with the files it created when the query's context closes, on success, failure, or kill; a shutdown hook closes the rest.
- Files hold `SpillBlocks`: one batch per block, columns as held in memory (primitives as arrays, strings as UTF-16 with per-row lengths, batch-entry strings and plain strings at most half distinct per block as entries and codes, BigDecimal decimals as scale and unscaled bytes). `AnyT` columns are not spillable, and holders over them reserve as before. No compression.
- Aggregation (`spill_aggregation`, on by default): `PartitionedAggOp` reads its input with `tryReserve`; past the threshold, `AggSpillRouter` cuts the buffered and remaining rows into chunks (4–64 MB, at most `parallelism` in flight and reserved), and tasks hash, gather, and encode each chunk per partition. The reader thread appends the blocks to 64 files in chunk order, so no task writes at close and partitions keep the input order. `AggSpill` then aggregates the files in waves of at least a quarter of the threshold, at twice each file's estimated bytes. A wave of one partition runs the in-memory parallel path over it; a wider wave runs one task per partition. A file needing more than half the threshold is split once with another hash seed (deeper, it runs anyway and meets the query limit). Each wave's reservations return when the next wave starts. See [the aggregation spill ADR](../adr/2026-11-27-engine-aggregation-spill.md).
- Not spilling yet: plain `HashAggOp` (global aggregates, morsel partials), `DistinctOp`, joins, sorts and windows, and shared CTE results.
- `AggSpillTest` (JVM) forces spills with tiny thresholds and checks groups against the in-memory run, the split path, cleanup after a failure, and the folder's permissions; `SpillBlocksTest` (shared, also on JS) checks the block format.

## Fair task scheduling

- `ThreadPoolRunner` (`TaskRunner.default`, JVM and Native copies of `exec/TaskRunnerCompatImpl.scala`) runs a task submitted from a thread in a `TaskGroup` on a pool that picks across groups (`exec/FairTaskQueue.scala`); a task submitted outside any group runs on the FIFO pool as before. Each pool starts on its first task. Behind `fair_task_scheduling` (on by default): `WvletEngine.execute` (and `asQuery`, which the benches use) opens a group per query unless one is current, so a nested `execute` (e.g. `TableWriter`) stays in its caller's group.
- A task learns its query from the submitting thread's `TaskGroup.current`, as operators learn their `MemoryContext`: pool threads set the task's group while it runs, and `coordinate` carries the group to coordinator threads, so tasks submitted from tasks stay in the query.
- `FairTaskQueue` is a multilevel feedback queue on each group's run time, like Trino's time-sharing executor: finished tasks' wall time plus the elapsed time of running ones. Levels start at 0, 1, 10, 60, and 300 s of run time (summed over threads). The next task comes from the non-empty level with the least run time weighted by 2^level, and a level that becomes non-empty starts at the least weighted time of the busy levels. Within a level, the group that has run least goes first, so a query of short tasks isn't outrun by one of long tasks, nor by a new query that has just taken every thread.
- Counting running tasks matters: with finished tasks only, a fresh long query tied the short ones at 0 ms and took all threads before its first task finished; within-level turns of one task each let 15 ms long-query tasks take ~90% of a level shared with 1.5 ms short-query tasks.
- Tasks are not preempted, so a short query waits for the running tasks of a long one (TPC-H lineitem morsels: 9–15 ms at SF10). GC pauses of a long query's large aggregations still stall every query (50–260 ms G1 pauses in the mixed bench).
- Coordinator tasks, behind `fair_coordinators` (on by default; no plan change): a group's coordinator tasks run on a second `FairPool` of half the parallelism, whose `FairTaskQueue(coordinators = true)` counts `TaskGroup.coordinatorNanos` instead of pool-task run time, since coordinators mostly wait. Ungrouped coordinator tasks stay on the FIFO pool. Every waiter on a coordinator handle also runs unstarted work on its own thread (`runTogether`, `StartSharedOp`, and with this toggle `computeSharedResults`), so a query never waits for a coordinator thread that other queries hold; `EngineConcurrentSharedCTEsTest` blocks every coordinator thread and checks that a query with joined shared CTEs still finishes.
- Yielding between batches was measured and not shipped ([plan](../plans/2026-11-27-fair-cpu-follow-ups.md)): SF10 lineitem morsel parts are one batch each, and the fair queue already gives a waiting short query the next free thread within about 1 ms, so running its tasks inline in a long query's task (even with batches cut into 16K-row slices) didn't move the mixed bench beyond its noise.
- `FairPool` submitters only append to a concurrent inbox and release a semaphore permit; workers drain the inbox into the queue under its lock, so submitters never wait for the workers. A single monitor shared by submitters and workers measured 2–7% slower on TPC-H SF1 wall.
- `FairTaskQueueTest` (shared, also on JS) checks levels, shares, and the within-level order with explicit times; `ThreadPoolRunnerFairTest` checks group propagation and that a short group's tasks run ahead of a long group's queued ones.

## Accelerators (GPU offload)

- A `PlanAccelerator` (`runtime/PlanAccelerator.scala`) is offered each runtime plan subtree top-down in `Lowering`, before CPU lowering; the first subtree it accepts runs as one operator. `WvletEngine(accelerator = ...)` sets one; the `gpu_offload` toggle turns the hook off. See [the GPU executor ADR](../adr/2026-11-24-engine-gpu-executor.md).
- `wvlet-engine-gpu` is the example accelerator (cudf-java, JVM only, not in the CLI pack or the CI aggregates). It runs subtrees that join or aggregate, keeps scanned columns on the device across queries, and runs a subtree on the CPU if the device fails at run time.
- `EnginePlanAcceleratorTest` checks the hook with a stub accelerator. On a machine with a CUDA device, `./sbt "engineGpu/testOnly *GpuTPCHTest"` checks spec/tpch against DuckDB with GPU offload (`WVLET_GPU_TEST_DATA=target/tpch-sf10` checks SF10), and `WVLET_ENGINE_BENCH_SF=10 WVLET_ENGINE_BENCH_AB=gpu_offload ./sbt "engineGpu/testOnly *GpuTPCHBench"` compares GPU on and off.
- After a planner change that adds or reshapes runtime plan nodes, run `./sbt "engineGpu/testOnly *GpuOffloadCoverageTest"` (no CUDA device needed; CI doesn't build `engineGpu`). It fails when a spec/tpch query gains a node the GPU doesn't run, and names it; teach the GPU the shape or add it to the test's known blockers. Debug logs of `GpuAccelerator` name the node that keeps each subtree on the CPU.
- Optimizations inside the GPU module are `GpuFeature`s rather than `Optimization` toggles, because they don't change engine plans: A/B one with `WVLET_GPU_BENCH_AB=<feature>` in the same bench. The module rewrites only its own subtrees (implied filters, join key filters, column pruning) and picks decimal widths from cached value bounds; see [the follow-up ADR](../adr/2026-11-24-gpu-executor-runtime-choices.md). The column cache also records per cached column whether it is sorted and a dictionary of low-cardinality strings, for sorted and coded group-bys; see [the column properties ADR](../adr/2026-11-24-gpu-column-properties.md).
- Tables over `WVLET_GPU_STREAM_ROWS` rows (default 100M) whose whole scan wouldn't fit stream through the GPU subtree in row ranges: partial aggregates merge on the device, joins probe a hash table built once, and string columns over cudf's 2 GB limit are cached in pieces. A subtree that would concatenate such a string column stays on the CPU at plan time. `GpuStreamTest` streams spec/tpch in small ranges against DuckDB; see [the chunked scans ADR](../adr/2026-11-24-gpu-chunked-scans.md).

## Benchmarks

- `EngineTPCHBench` and `EngineTPCDSBench` run the spec queries on the engine and on DuckDB over the same Parquet files. They are ignored unless `WVLET_ENGINE_BENCH_SF` is set. The other `WVLET_ENGINE_BENCH_*` variables are listed in the bench classes' Scaladoc and in [the benchmark guide](../website/docs/development/benchmark.md).
- A/B an engine change behind its `Optimization` toggle in one JVM: `WVLET_ENGINE_BENCH_SF=1 WVLET_ENGINE_BENCH_RUNS=5 WVLET_ENGINE_BENCH_AB=<toggle> ./sbt "engineJVM/testOnly *EngineTPCHBench *EngineTPCDSBench"`. Read the suite on/off totals first; single queries are noisy.
- A change that cannot be toggled is benchmarked against an origin/main worktree, alternating rounds between the two trees.
- `EngineMixedWorkloadBench` times a stream of short TPC-H queries alone and next to a long query running in a loop, with `fair_task_scheduling` on and off in alternating rounds: `WVLET_ENGINE_BENCH_SF=10 WVLET_ENGINE_MIXED_BENCH=1 ./sbt "engineJVM/testOnly *EngineMixedWorkloadBench"` (`WVLET_ENGINE_MIXED_SHORT=q11`, `WVLET_ENGINE_MIXED_LONG=<query or SQL>`). `WVLET_ENGINE_MIXED_TOGGLE` names the toggles the off rounds disable (default `fair_task_scheduling`). It also logs each query's pool task time and mean task length, and per round the GC time and the stop-the-world pauses (count, total, longest).
